# テニス乱数表アプリ 要件定義書 v1

## 1. 文書の目的

本書は、テニスのダブルス練習やサークル活動において、参加者の出場・休憩・ペア・対戦相手の偏りをできるだけ抑えながら、1試合ずつ組み合わせを決定する「テニス乱数表アプリ」の要件を定義するものである。

本アプリは新規開発とし、既存コードは存在しない。

本書を今後の設計・実装・テストの基準とする。

---

# 2. アプリ概要

## 2.1 目的

テニスのダブルス練習において、参加者の試合数や休憩回数をできるだけ公平にしながら、毎試合の4人を自動的に決定する。

複数試合分の乱数表を最初に一括作成する方式ではなく、実際の進行に合わせて1試合ずつ組み合わせを決定する。

基本フローは以下とする。

1. 現在までの試合履歴を保持する
2. 次の1試合の組み合わせを計算する
3. 「次の試合」ボタン押下時点で確定する
4. 履歴へ追加する
5. 次の試合生成時に過去履歴を反映する

# 4. 基本仕様

## 4.1 テニス形式

- ダブルスのみ
- 1試合4人
- 基本は1コート
- シングルスは対象外
- 複数コートはv1では対象外

## 4.2 参加人数

参加人数は以下とする。

- 5人
- 6人
- 7人

4人以下は対象外とする。

8人以上もv1では対象外とする。

---

# 5. 試合途中の人数変更

試合セッション開始後でも参加人数を変更可能とする。

例：

- 7人 → 6人
- 6人 → 5人
- 5人 → 6人
- 6人 → 7人

途中参加・途中退出の双方を想定する。

人数変更後も、それまでの試合履歴は保持する。

## 5.1 人数減少時

参加人数を減らした場合、対象外となったプレイヤーは以後の組み合わせ生成対象から除外する。

例：

7人から5人へ変更した場合、プレイヤー6・7を非参加状態とする。

過去履歴は削除しない。

## 5.2 人数増加時

参加人数を増やした場合、新しく追加されたプレイヤーを参加状態とする。

例：

5人から7人へ変更した場合、プレイヤー6・7を新規参加させる。

新規プレイヤーの初期値は以下とする。

- 試合数：0
- 休憩回数：0
- 連続出場数：0
- 連続休憩数：0
- 最大連続出場：未設定

---

# 6. プレイヤー表示

プレイヤー名は使用しない。

数字のみで管理する。

参加人数7人の場合、

1 / 2 / 3 / 4 / 5 / 6 / 7

とする。

---

# 7. 現在試合のプレイヤー表示

現在の試合では、

- 出場プレイヤー
- 休息プレイヤー

の2段表示とする。

表示例：

```text
出場プレイヤー
①×2   ③×1   ④×3   ⑥×1

① ③
 VS
④ ⑥

休息プレイヤー
②   ⑤
```

---

# 8. 履歴表示位置

試合履歴はメイン画面の上部に表示する。

表示順の基本構成は以下とする。

```text
ヘッダー
↓
試合履歴
↓
現在／次の試合
↓
操作ボタン
↓
プレイヤー設定
↓
統計
```

履歴は画面下部ではなく、現在試合より上に配置する。

iPhoneで画面を開いた際に、直近の試合状況と次の試合を連続して確認できる構成とする。

---

# 9. 履歴と次の試合のレイアウト統一

履歴の各試合は、「現在の試合」「次の試合」と同じ基本レイアウトで表示する。

履歴専用の表形式や一行形式にはしない。

例えば現在試合が以下の場合、

```text
第8試合

出場プレイヤー
①×2   ③×1   ④×3   ⑥×1

① ③
 VS
④ ⑥

休息プレイヤー
②   ⑤
```

過去履歴も同じ形式とする。

例：

```text
第7試合

出場プレイヤー
①   ②   ⑤   ⑥

① ⑤
 VS
② ⑥

休息プレイヤー
③   ④
```

これにより、過去試合と現在試合を同じ視覚ルールで確認できるようにする。

---

# 10. 履歴表示順

履歴は最新試合を上に表示する。

例：

```text
第7試合
第6試合
第5試合
第4試合
...
```

その下に現在または次の試合を表示する。

ただし、画面上で最新の履歴と現在試合の区別が分かるように、見出しや背景の違いを設ける。

---

# 11. 履歴の表示件数

履歴は全件保持する。

画面上では、iPhoneでの縦長化を防ぐため以下の方式を検討する。

推奨仕様：

- 直近3〜5試合を初期表示
- 「履歴をもっと見る」で追加表示
- localStorage上では全履歴を保持

ただし、v1で実装を単純化する場合は全件表示でもよい。

---

# 12. 現在試合と履歴の視覚的区別

レイアウトは統一するが、状態は視覚的に区別する。

例えば、

- 現在試合：強調背景
- 履歴：通常背景
- 最新履歴：少し強調
- 過去履歴：控えめ

とする。

ただし、構造そのものは統一する。

---

# 13. 次の試合

「次の試合」ボタンを主要操作とする。

タップすると、

- 次の出場者を決定
- ペアを決定
- 試合を確定
- 履歴へ追加
- 統計更新
- localStorage保存

を行う。

別途「確定」ボタンは設けない。

---

# 14. 最新試合の取消

直前の1試合だけ取消可能とする。

「前の試合を取消」によって、

- 最新履歴削除
- 試合数復元
- 休憩数復元
- 連続出場数復元
- 連続休憩数復元
- ペア回数復元
- 対戦回数復元

を行う。

2試合以上前の試合を直接削除する機能は設けない。

---

# 15. 手動組み合わせ変更

現在表示中の確定試合について、プレイヤー番号をタップして入れ替えできる。

操作は、

1. 交換元プレイヤーをタップ
2. 交換先プレイヤーをタップ
3. 2人を交換

とする。

交換可能範囲は以下。

- 出場者同士
- 出場者と休息者
- 休息者同士

履歴上の過去試合は直接編集しない。

---

# 16. 最大連続出場回数

各プレイヤーごとに個別設定可能とする。

設定値は以下を想定する。

- 未設定
- 1
- 2
- 3
- 4
- その他必要な範囲

## 16.1 未設定

「未設定」は上限なしを意味する。

## 16.2 デフォルト

全プレイヤーの初期値は未設定とする。

---

# 17. 最大連続出場制約

最大連続出場回数が設定されているプレイヤーについては、その回数を原則として超えない。

ただし、組み合わせ成立が難しい場合は自動的に制約を緩和する。

---

# 18. 組み合わせ不能時の扱い

「現在の条件では組み合わせを作成できません。」という確認ダイアログは表示しない。

組み合わせ生成が困難な場合は、

1. 強制休息を優先
2. 最大連続出場制約を一時的に緩和
3. 違反が最小となる候補を選択

とする。

必要に応じて、

「連続出場上限を一時的に超えて組み合わせを作成しました。」

などの非ブロッキング通知は表示可能とする。

---

# 19. 強制休息

特定プレイヤーを「次の1試合だけ休息」に指定可能とする。

試合作成後に自動解除する。

複数指定可能とする。

ただし、出場可能者が4人未満になる指定は受け付けない、または自動調整する。

---

# 20. 連続出場回数の可視化

各プレイヤーについて、現在何試合連続で出場しているか分かるようにする。

例：

```text
①×1
③×2
④×3
⑥×1
```

または同等の表現を使用する。

---

# 21. 連続出場回数の色表示

連続出場数に応じてプレイヤー番号または背景色を変える。

例：

| 連続出場 | 表示 |
|---|---|
| 0 | 通常 |
| 1 | 弱い強調 |
| 2 | 中程度の強調 |
| 3 | 強い強調 |
| 4以上 | 警告レベル |

具体的な色はCSSで定義する。

色だけで判断しなくてもよいよう、数値も併記する。

---

# 22. 履歴内の連続出場表示

履歴についても、基本レイアウトは現在試合と統一する。

ただし履歴内の連続出場数は、「その試合終了時点での値」を表示できる構造が望ましい。

そのため、必要に応じて試合履歴にスナップショット情報を保存する。

例：

```javascript
streakSnapshot: {
  1: 2,
  3: 1,
  4: 3,
  6: 1
}
```

これにより、過去試合を現在の連続出場数で誤表示しないようにする。

---

# 23. 組み合わせ生成方針

完全ランダムではなく、公平性を考慮した組み合わせ生成とする。

過去履歴を参照して候補を評価する。

---

# 24. 公平性の優先順位

以下の順に優先する。

1. 最大連続出場制限・強制休息
2. 試合数の均等化
3. 連続休憩回避
4. 連続出場の偏り抑制
5. ペア重複回避
6. 対戦相手重複回避

---

# 25. 出場者候補生成

現在参加中のプレイヤーから4人を選択する全候補を生成し、評価する。

---

# 26. 試合数の均等化

累計試合数が少ないプレイヤーを優先する。

途中参加者も同様に扱う。

---

# 27. 休憩の均等化

休憩回数が偏らないようにする。

---

# 28. 連続休憩回避

同じプレイヤーが連続で休憩することを可能な限り避ける。

---

# 29. 連続出場偏り抑制

最大連続出場が未設定でも、特定プレイヤーだけが長く連続出場しないよう評価する。

---

# 30. ペア重複回避

同じ2人のペアが繰り返されることをできるだけ避ける。

---

# 31. 対戦相手重複回避

同じ相手との対戦ばかりにならないようにする。

---

# 32. ペア決定

4人の出場者が決定した後、3種類のペア分けを評価する。

例：

- 1・2 vs 3・4
- 1・3 vs 2・4
- 1・4 vs 2・3

ペア履歴・対戦履歴を考慮する。

---

# 33. ランダム性

評価が同等の候補が複数ある場合、その中からランダム選択する。

---

# 34. 管理するプレイヤー情報

各プレイヤーについて以下を保持する。

- プレイヤー番号
- 参加状態
- 試合数
- 休憩回数
- 現在の連続出場数
- 現在の連続休憩数
- 最大連続出場設定
- 次試合強制休息状態

---

# 35. 試合履歴データ

各試合について最低限以下を保存する。

- 試合番号
- Team A
- Team B
- 休息者
- 参加プレイヤー一覧
- timestamp
- 必要に応じて連続出場数スナップショット

例：

```javascript
{
  matchNumber: 8,
  activePlayers: [1, 2, 3, 4, 5, 6],
  teamA: [1, 3],
  teamB: [4, 6],
  resting: [2, 5],
  streakSnapshot: {
    1: 2,
    3: 1,
    4: 3,
    6: 1
  },
  timestamp: 1720000000000
}
```

---

すべての状態をlocalStorageに保存する。

保存対象は以下。

- 参加人数
- 参加状態
- 現在試合番号
- 試合履歴
- 試合数
- 休憩数
- 連続出場数
- 連続休憩数
- 最大連続出場設定
- 強制休息設定
- ペア履歴
- 対戦履歴
- UIに必要な設定

---

# 37. 保存タイミング

以下の操作時に保存する。

- 次の試合作成
- 手動交換
- 最新試合取消
- 人数変更
- 最大連続出場設定変更
- 強制休息変更

# 42. 履歴レイアウト共通化

履歴と現在試合は、同じUIコンポーネントまたは同じ描画関数を利用できる構造を推奨する。

例えば、

```javascript
renderMatchCard(match, options)
```

のような共通関数を使用し、

- 履歴表示
- 現在試合表示

の双方で使える設計とする。

これにより、レイアウト変更時の保守性を高める。

# 53. 受け入れ条件

## 履歴表示

- 履歴がメイン画面上部に表示される
- 最新履歴が最上部に表示される
- 履歴と現在試合の基本レイアウトが同一である
- 出場プレイヤーと休息プレイヤーが履歴内でも2段表示される
- 過去試合と現在試合が視覚的に区別できる
- 履歴を表示してもiPhoneで操作性が著しく損なわれない

## 参加人数

- 5人で利用できる
- 6人で利用できる
- 7人で利用できる
- 試合途中に人数変更できる
- 人数変更後も過去履歴が保持される

## 最大連続出場

- 各プレイヤーごとに設定可能
- 未設定を選択可能
- デフォルトは未設定
- 未設定時は上限なし
- 制約違反が必要な場合は自動緩和される

## 連続出場表示

- 現在の連続出場数が分かる
- 数字表示がある
- 連続数に応じて色が変化する

## 強制休息

- 次の1試合だけ指定できる
- 試合作成後に解除される

## 手動変更

- 数字を2回タップして交換できる
- 出場者と休息者を交換できる

## 履歴取消

- 最新試合だけ取消できる
- 取消後に統計が正しく戻る

## 保存

- Safariを閉じても状態を保持する
- 次回起動時に状態を復元する

# 54. 実装上の重要原則

1. 履歴は画面上部に配置する。
2. 履歴と現在試合は同じレイアウト構造を使用する。
3. 同一の試合カード描画処理を再利用できる設計を推奨する。
4. 現在試合と過去履歴は背景・見出しなどで区別する。
5. 履歴は最新試合を上に表示する。
6. 過去履歴の連続出場表示は、必要に応じて当時のスナップショットを使用する。
7. 人数変更で過去履歴を削除しない。
8. 最大連続出場の未設定は`null`等で表現する。
9. デフォルトは全員未設定とする。
10. 出場者と休息者を常に2段表示する。
11. 連続出場回数は色と数字の両方で確認可能にする。
12. 組み合わせ不能時に確認ダイアログを出さない。
13. 強制休息は最大連続出場条件より優先する。
14. UIコードと組み合わせ生成ロジックを分離する。
15. localStorageにデータバージョンを持たせる。
16. iPhone縦画面での操作性を最優先する。
17. PWA化を妨げない構成とする。

以上を「テニス乱数表アプリ v1」の要件とする。
