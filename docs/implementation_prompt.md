# テニス乱数表アプリ v1 実装指示書

## 目的と参照元

このリポジトリに、1コート・ダブルス・参加者5〜7人向けの「テニス乱数表アプリ v1」を実装してください。仕様の一次資料は [要件定義書](./requirements.md) です。本書は実装時の作業指示と検証観点を整理したものです。記載が食い違う場合は要件定義書を優先し、採用した解釈を README に残してください。

試合は「次の試合」を押すたびに1件だけ生成・確定します。過去の試合を使って出場、休憩、ペア、対戦相手の偏りを抑えます。画面は iPhone の縦向きを優先し、Safari、Chrome、Edge の比較的新しいバージョンで使えるようにしてください。

## 完成条件

- HTML、CSS、素の JavaScript（ES Modules）で動作する。通常利用にサーバー、外部通信、ログイン、外部フレームワークを必要としない。
- 5、6、7人のいずれでも試合を生成でき、試合途中に人数を増減しても過去履歴が残る。
- 履歴、現在の試合、設定、統計、手動交換、直前の取消、新しいセッション、保存と復元が一通り動く。
- 要件定義書の受け入れ条件を確認し、実行方法と確認結果を README に記載する。

## 実装順序

1. アプリの基本画面と、単一の `state` から描画する仕組みを作る。
2. 参加人数・プレイヤー設定・試合履歴のデータ構造と、保存・復元・検証を作る。
3. 組み合わせ生成、統計更新、取消、手動交換を実装する。
4. 履歴と現在試合の共通カード、モバイル向け操作、設定・統計表示を実装する。
5. 下記の確認ケースを実行し、欠けた動作を修正する。

推奨構成は `index.html`、`css/style.css`、`js/app.js`、`js/state.js`、`js/matchGenerator.js`、`js/scoring.js`、`js/storage.js`、`js/ui.js`、`README.md` です。責務は要件定義書の第45〜47章に合わせてください。必要なら小さな補助モジュールを追加できます。PWA 用の manifest、Service Worker、アイコンは v1 の必須機能ではありませんが、後から追加しやすい相対パス構成にしてください。

## データと状態遷移

- プレイヤー ID は `1`〜`7` の数字とし、現在の参加者は常に `1`〜`participantCount` とする。初期人数は有効範囲内から選ぶ。名前は扱わない。
- プレイヤーごとに参加状態、試合数、休憩回数、連続出場数、連続休憩数、最大連続出場設定、次試合だけの強制休息を管理する。最大連続出場の未設定は `null` など明確な値で表し、初期値は全員未設定とする。
- 各試合には試合番号、当時の参加者一覧、2人ずつの両チーム、当時の休息者、確定時刻、試合終了時点の連続出場数スナップショットを保存する。チームと休息者は重複せず、当時の参加者全員をちょうど一度ずつ含める。
- 履歴配列は確定済み試合の記録とする。画面の「現在の試合」はその最新試合を参照する。初回生成前は試合カードの代わりに開始案内を表示する。「次の試合」はプレビューや別の確定操作を挟まず、押下時に生成・記録する。
- 試合番号はセッション内で 1 から連番とする。取消後は次の生成で取り消した番号を再利用する。手動交換では試合番号と確定時刻を変えない。
- 人数を減らすと、上位の ID を以後の候補から外す。人数を増やすと、新規 ID はゼロの統計と未設定の上限で参加させる。過去に参加した ID が再参加する場合は既存履歴と累計統計を保持し、退出中の連続出場・休憩は継続しない。人数変更は過去試合の参加者一覧を変更しない。
- 統計、ペア回数、対戦回数と履歴の整合性を保つ。特に手動交換・取消・人数変更後は再計算、または同等の安全な更新を行う。履歴スナップショットも、交換により値が変わる試合について更新する。参加・退出をまたぐ連続数を正しく扱えるよう、必要なら人数変更のイベントを保持する。
- 強制休息は次に生成する1試合に適用し、その試合を確定した後で解除する。出場可能者が4人未満になる設定は受け付けず、理由を画面で伝える。試合生成時は有効な強制休息を必ず守る。
- 最大連続出場の上限は原則守る。強制休息を守ったまま4人を選べない場合だけ上限を緩和し、違反が最小の候補を選ぶ。制約緩和が起きたら必要に応じて非ブロッキング通知を出す。組み合わせ不能を理由とする確認ダイアログは出さない。
- 手動交換は最新の確定試合だけで行う。出場者同士、出場者と休息者、休息者同士のいずれも2タップで交換できる。交換後は履歴・統計・連続数・ペア/対戦回数・保存内容・画面を整合させる。過去試合は直接編集できない。
- 「前の試合を取消」は最新の1試合のみを削除する。確定前の状態へ統計を戻し、取り消した試合に適用された一時設定をどう扱うかは実装内で一貫させて README に記載する。履歴が空なら操作できない。
- 「新しいセッション」は履歴、試合番号、統計、ペア/対戦回数、強制休息を初期化し、最大連続出場設定と参加人数は保持する。

### 保存と復元

`localStorage` にデータバージョン付きで必要な状態を保存してください。次の試合、手動交換、取消、人数変更、上限変更、強制休息変更、新しいセッションの各操作後に保存します。起動時は保存データの型・範囲・試合構造を検証して復元します。破損や未知バージョンの場合に画面が停止しないよう、安全な初期状態へ戻す処理と利用者への簡潔な通知を用意してください。ブラウザを閉じて開き直しても、履歴と設定が復元されることを確認してください。

## 組み合わせ生成

現在の参加者から4人の全組み合わせを列挙し、各4人について3通りのペア分けを評価してください。候補数は最大でも `C(7,4) × 3 = 105` なので、ブラウザ内で同期計算できます。

評価の優先順位は以下の通りです。上位条件の大きな悪化を下位条件の改善で相殺しないよう、段階的な絞り込みや辞書式比較など、比較方法を明示して実装してください。

1. 強制休息を満たす。最大連続出場は成立する限り守り、やむを得ない緩和では違反人数・超過量を最小化する。
2. 累計試合数を均等化し、途中参加者を含めて試合数が少ない人を優先する。休憩回数の偏りも評価する。
3. 連続休憩を避ける。
4. 上限未設定の人も含めて連続出場の偏りを抑える。
5. 同じペアの反復を避ける。
6. 同じ相手との対戦の反復を避ける。

同評価の候補が複数ある場合は、その中からランダムに選びます。ペア・対戦の回数は二人組の順序に依存しないキーで集計してください。生成関数は DOM と `localStorage` に依存させず、入力状態から候補を返す形にしてください。公平性は絶対保証ではなく、上記の優先順位に従って候補を比較することを目標とします。

## 画面と操作

画面の縦方向の順番は「ヘッダー → 試合履歴 → 現在の試合 → 操作ボタン → プレイヤー設定 → 統計」です。履歴は新しい試合から上に並べ、現在試合と同じカード構造で表示してください。カード内では「出場プレイヤー」およびチームの対戦表示の下に「休息プレイヤー」を置きます。最新履歴・古い履歴・現在試合は見出しや背景で区別してください。現在試合が履歴の最新試合と同一であることを表示から理解できるようにしてください。

iPhone 縦向きで履歴が長くなりすぎないよう、初期表示は直近 3〜5 試合とし、「履歴をもっと見る」で追加表示できるようにしてください。保存する履歴は全件です。プレイヤーの連続出場数は数字と色の両方で示し、履歴ではその試合終了時点の値を表示してください。色だけを手掛かりにしないでください。

「次の試合」「前の試合を取消」、プレイヤー番号、強制休息の操作領域は目安として 44px 以上とします。交換の選択状態を見えるようにし、キーボード操作・フォーカス表示・押下状態の伝達にも配慮してください。画面幅が狭くても横スクロールなしで主要操作を行えるようにしてください。人数変更、上限設定、強制休息、統計の表示を用意してください。

## 検証項目

少なくとも次を確認し、結果を README に短く記録してください。ロジックについては、必要に応じて小さな自動テストを作成してください。

1. 5・6・7人で連続して試合を生成しても、毎試合の出場者は4人、残りは休息者であり、参加者の重複・欠落がない。
2. 7→5→7 の人数変更後も以前の履歴が残り、各試合カードに当時の参加者が表示される。新規参加・再参加の統計が説明した仕様に従う。
3. 強制休息を複数指定でき、出場可能者が4人未満になる指定は拒否され、次の試合確定後に指定が解除される。
4. 上限を守れる場合は守り、守れない場合も4人を選んで制約違反を最小化する。上限未設定は制限しない。
5. 手動交換の3種類を試し、最新試合の表示、履歴、統計、ペア/対戦回数、連続数が一致する。
6. 最新試合を取り消すと、試合番号・統計・履歴・連続数が正しく戻る。空履歴で取消を押しても壊れない。
7. リロードやブラウザ再起動で人数、設定、履歴、統計が復元される。破損した保存データでも起動できる。
8. iPhone 縦向き相当の画面幅で、履歴、現在試合、操作ボタンが読みやすく押しやすい。Safari、Chrome、Edge で基本操作を確認する。

## 完了時の報告

実装した機能、確認した内容と結果、残る制約があれば簡潔に報告してください。要件定義書に書かれていない判断をした場合は、その判断を README に記載してください。対象外機能（4人以下・8人以上、複数コート、シングルス、名前、スコア、ログイン、クラウド同期など）は追加しないでください。
