# テニス乱数表アプリ 4〜8人対応 実装指示書

## 1. 目的と参照元

現行の1コート・ダブルス向けテニス乱数表アプリを、参加者5〜7人対応から4〜8人対応へ拡張してください。

仕様の一次資料は [4〜8人対応 要件定義書](./requirements_4_to_8.md) です。既存仕様は [v1要件定義書](./requirements.md)、既存実装の背景は [v1実装指示書](./implementation_prompt.md) と [v1進捗管理](./progress.md) を参照してください。本書と要件定義書が食い違う場合は、4〜8人対応要件定義書を優先します。

実装状況は [4〜8人対応 進捗管理](./progress_4_to_8.md) に記録してください。完了した事実だけをチェックし、未検証項目を完了扱いにしないでください。

## 2. 実装方針

- HTML、CSS、素のJavaScript（ES Modules）という現在の技術構成を維持する。
- サーバー、外部通信、ログイン、外部フレームワーク、追加ランタイム依存を導入しない。
- 単一の `state` と時系列イベントから画面・統計を再構築する既存設計を維持する。
- 試合数、休息数、連続数、ペア回数、対戦回数をDOM上の値から復元しない。
- 公平性評価の優先順位と辞書式比較を変更しない。
- iPhone優先のUI、Safe Area、PWA、タッチ操作、キーボード操作を維持する。
- 対応人数の拡張に必要のないリファクタリングや機能追加は行わない。
- 既存の5〜7人の動作を回帰させない。

## 3. 完成条件

- 4・5・6・7・8人のいずれでも、1試合4人のダブルスを生成できる。
- 4〜8人の範囲で人数変更しても、過去履歴と累計統計が保持される。
- プレイヤー8が状態、設定、生成、履歴、統計、交換、保存の全処理で他プレイヤーと同様に扱われる。
- 4人時は全員出場、休息者0人、強制休息不可として動作する。
- 8人時は出場4人・休息4人となり、最大4人の強制休息を指定できる。
- 現行の正常なバージョン1保存データを、履歴と設定を失わず新形式へ移行できる。
- 要件定義書の受け入れ条件、自動テスト、ブラウザ確認を実施し、結果と未確認事項を記録する。

## 4. 実装順序

以下のPhase順に進めてください。各Phaseの自動確認が通るまで、原則として次のPhaseへ進まないでください。

### Phase 0：変更前の確認

1. `docs` 内の要件定義書、実装指示書、進捗管理、UI設計指示書をすべて確認する。
2. `README.md` と既存実装を確認し、人数上限が記述・実装されている箇所を洗い出す。
3. 変更前に `npm test` とJavaScript構文チェックを実行し、基準結果を進捗管理へ記録する。
4. 作業開始時点の未コミット変更を確認し、利用者の変更を上書きしない。

### Phase 1：人数・プレイヤー状態の拡張

1. 対応人数を4〜8人、プレイヤーIDを1〜8へ拡張する。
2. 初期人数は5人のまま維持する。
3. 人数やIDの定義が `state.js`、`storage.js`、`ui.js` でずれないよう、必要なら小さな共有定義を追加する。
4. `createInitialState` と `changeCount` が4〜8人だけを受け付けるようにする。
5. プレイヤー8の最大連続出場初期値を未設定にする。
6. 退出・再参加時の累計値保持と連続数リセットを、4および8を含む変更でも維持する。
7. 4人へ変更した場合は強制休息をすべて解除する。
8. 人数減少後の強制休息は、非参加IDを除外し、出場可能者が4人以上となる状態へ正規化する。

Phase 1完了時に、4・8人の初期状態と `4→8→4`、`8→4→8` の状態遷移を自動テストで確認してください。

### Phase 2：保存形式と移行

1. 保存データのペイロードバージョンを新しい番号へ更新する。
2. 既存の保存キーからバージョン1データを発見できる状態を維持する。保存キーを変更する場合は、旧キーの読込と新キーへの移行を実装する。
3. バージョン1の正常データを検証し、プレイヤー8の最大連続出場設定を `null` として補完する。
4. 既存の参加人数、人数変更イベント、試合イベント、プレイヤー1〜7の設定、強制休息を保持する。
5. 移行後の統計とスナップショットをイベント履歴から再計算する。
6. 新形式では参加人数4〜8、ID 1〜8、休息者数0〜4、強制休息数 `参加人数 - 4` 以下を検証する。
7. バージョン1移行結果を新形式で保存し、その後の再読込でも同じ状態を復元できるようにする。
8. 破損データ、未知バージョン、不正な8人データは安全な初期状態へ戻し、既存と同様の通知を表示する。

Phase 2完了時に、旧形式移行、新形式保存復元、破損・未知バージョンのテストを通してください。履歴が消えた状態を「移行成功」として扱わないでください。

### Phase 3：組み合わせ生成と試合操作

1. 4〜8人から4人を選ぶ全候補と、各候補の3通りのペア分けを生成する。
2. 8人時の最大候補数 `C(8,4) × 3 = 210` を同期処理で評価する。
3. 強制休息、上限違反人数、超過量、試合・休息の均等、連続休息、連続出場、ペア、対戦相手の既存評価順を維持する。
4. 同評価候補からランダムに選ぶ既存動作を維持する。
5. 4人時は全員を出場させ、3通りのペア分けだけを評価する。
6. 4人時に最大連続出場上限を守れなくても生成を止めず、制約緩和として通知する。
7. 8人時に最大4人まで強制休息を許可し、5人目は既存指定を変えず拒否する。
8. 試合確定後に強制休息を解除する。
9. 4〜8人で、手動交換、最新試合取消、新しいセッションの整合性を維持する。
10. プレイヤー8を含むペア回数・対戦回数・スナップショットを正しく再計算する。

Phase 3完了時に、全人数の連続生成、強制休息、上限緩和、3種類の交換、取消、新しいセッションを自動テストで確認してください。

### Phase 4：UI・アクセシビリティ

1. 人数選択へ4人と8人を追加する。
2. 8人分の設定行と統計を描画する。
3. 4人時は休息プレイヤー欄を表示しない。
4. 8人時は休息者4人を欠落なく表示する。
5. 4人時の強制休息操作は、理由を理解できる補足付きで無効化するか、操作時に非ブロッキング通知で拒否する。
6. 強制休息の指定上限を超えた場合は、既存指定を維持し理由を表示する。
7. プレイヤー8の操作領域、交換選択、最大連続出場設定を他プレイヤーと同じ規則で描画する。
8. `data-swap-id`、`aria-pressed`、フォーカス表示、約44px以上の主要タップ領域を維持する。
9. Safe Area、ホーム画面からのstandalone表示、Service Worker登録を壊さない。
10. 幅320px、390px、768pxで横スクロール、文字重なり、操作不能がないことを確認する。

### Phase 5：総合検証と文書更新

1. `npm test` を実行する。
2. `js/*.js` と `sw.js` の構文チェックを実行する。
3. `manifest.webmanifest` のJSON構文を確認する。
4. 要件定義書の受け入れ条件を項目ごとに確認する。
5. ブラウザで4人と8人を中心に、試合作成、人数変更、強制休息、上限、交換、取消、新しいセッション、再読込を確認する。
6. 既存の5・6・7人テストを回帰テストとして実行する。
7. `README.md` の対応人数、操作、保存形式、移行、検証結果を更新する。
8. [進捗管理](./progress_4_to_8.md) に実行環境、件数、結果、未検証事項を記録する。
9. Safari実機、Edge、ブラウザ完全終了後の復元を実施できなかった場合は、未検証のまま明記する。

## 5. ファイル別の作業指示

### `js/state.js`

- プレイヤーIDを1〜8へ拡張する。
- 対応人数を4〜8へ拡張する。
- 4人時の強制休息禁止と、4人へ変更した際の指定解除を実装する。
- 既存のイベント再計算、退出時の連続数切断、再参加時の累計保持を維持する。
- 交換・取消・新しいセッションの仕様を変更しない。

### `js/matchGenerator.js`

- 4〜8人の候補列挙に対応する。
- 4人時の3候補、8人時の最大210候補を正しく扱う。
- DOMや保存処理への依存を追加しない。

### `js/scoring.js`

- 参加人数に基づく評価対象が4〜8人で正しく構築されることを確認する。
- 評価ベクトルの項目と優先順位を変更しない。
- 4人時の空の休息者によって `NaN` や例外が発生しないようにする。

### `js/storage.js`

- 新旧保存形式の検証と移行を実装する。
- 旧データの正常項目を保持し、プレイヤー8だけを未設定で補完する。
- 新形式では4〜8人、ID 1〜8、人数別の休息者数を検証する。
- 保存済みスナップショットと再計算結果の整合性検証を維持する。

### `js/ui.js`

- 4・8人の人数選択、プレイヤー8の設定・統計、休息者0人表示を追加する。
- 8人表示で既存のiOS風レイアウトと操作性を維持する。
- 無効状態と拒否理由を色だけに依存せず伝える。

### `js/app.js`

- 状態変更後の保存と再描画という既存の流れを維持する。
- 4人時の休息者0人、8人時の休息者4人を扱うプレビュー・表示用データに固定長の仮定を残さない。

### `test/app.test.js`

- 既存テストを削除せず、4〜8人対応のテストへ拡張する。
- 乱数を固定できる既存の設計を利用し、再現可能なテストにする。
- 保存移行テストでは、実際のバージョン1形式のfixtureを使う。

### `README.md` と `docs/progress_4_to_8.md`

- 実装した事実と確認した結果だけを記載する。
- 保存形式の変更、旧データ移行、4人時の特則、8人時の強制休息上限を説明する。
- 未実施のブラウザ検証を成功扱いにしない。

## 6. 必須自動テスト

最低限、次をテストしてください。

1. 4〜8人で各40試合以上生成し、出場4人と休息 `人数 - 4` 人に重複・欠落がない。
2. 4人時は休息者、休息連続数スナップショットが空で、休息数が増えない。
3. 4人時のペア分けが3通りから評価される。
4. 8人時は休息者が4人で、プレイヤー8が出場・休息候補になる。
5. `4→8→4` と `8→4→8` で履歴と累計を保持し、退出をまたぐ連続数が切れる。
6. 4人時の強制休息指定を拒否する。
7. 8人時に強制休息4人を指定でき、5人目を拒否し、確定後に解除する。
8. 4人時に最大連続出場上限が不可避でも生成し、制約緩和を通知する。
9. 8人時に守れる上限を守り、不可避時は違反を最小化する。
10. プレイヤー8を含む出場者同士、出場者と休息者、休息者同士の交換で統計が再計算される。
11. 4人・8人で取消後に番号、履歴、統計が戻る。
12. 新しいセッションが人数と1〜8の最大連続出場設定を保持する。
13. 新形式で4人・8人の状態を保存・復元できる。
14. 正常なバージョン1データを履歴・設定を失わず移行できる。
15. 破損データ、未知バージョン、不正な人数・ID・試合構造から安全に復旧する。

## 7. ブラウザ確認

幅320px、390px、768pxを最低限確認し、次を記録してください。

- 4人時に休息プレイヤー欄が表示されず、強制休息不可の説明があること
- 8人分の設定、統計、休息者4人の表示
- 4人と8人での試合作成
- `4→8→4` と `8→4→8` の人数変更
- 8人時の強制休息4人と5人目の拒否
- プレイヤー8を含む交換
- 取消、新しいセッション、再読込後の復元
- 横スクロール、重なり、タップ困難な領域がないこと
